# Удаление аккаунта и согласование подписок

## Scope

Проект процесса подготовлен по запросу владельца. Процесс подписок не реализован
и не одобрен для production. Документ не разрешает выбор провайдера, реальные
платёжные вызовы, возвраты, миграции или удаление бухгалтерских документов.

## Согласованное поведение (2026-09-04)

- Сразу отключить продление; сохранить доступ и данные до конца оплаченного
  периода. Назначить удаление на эту дату, показывать «Удаление запланировано».
- До наступления этой даты пользователь может отменить удаление. Это не
  восстановление стёртых данных. Отмена удаления не включает автопродление:
  возобновление подписки требует отдельного явного действия.
- В назначенную дату начать окончательное удаление, если оно не отменено.
  После окончательного удаления восстановление невозможно.
- Отдельный выбор «Удалить сейчас» запускает блокировку и процесс удаления без
  ожидания окончания оплаты; его нельзя подменять отложенным сценарием.
- Обычная отмена не запускает автоматический возврат, поскольку оплаченный
  доступ сохраняется. Законные права на отказ и возврат не ограничиваются;
  возвраты, спорные платежи и выставленные счета рассматриваются отдельно.
- Отключение продления считается успешным только после подтверждения провайдера.
- Без оставшегося оплаченного периода отсрочки до даты оплаты нет.

Текущий код блокирует аккаунт сразу; отложенный сценарий ещё не реализован.
Добровольное планирование не переопределяет сроки окончательного удаления.
Юридическая проверка перед production остаётся обязательной.

## Реализованный фундамент (не подключён к продукту)

В `packages/backend/src/identity/scheduled-deletion-policy.ts` добавлены чистые
правила планирования, отмены и наступления срока. Они учитывают конец оплаченного
доступа, не принимают неподтверждённую отмену продления за успех, не разрешают
отмену с момента срока удаления и не возобновляют подписку. «Удалить сейчас»
не задерживается из-за недоступной сверки платежей; это не означает завершения
удаления у processors. Даты и подтверждения должен передавать только сервер.

API, таблицы, worker и интерфейс ещё не подключены. Для них требуется согласовать
общую billing-границу: application port в packages/backend, который используют
API и worker, с адаптером провайдера и устойчивыми операциями в PostgreSQL.
Защита гонки «отменить/удалить» должна быть транзакционной, а не только проверкой
чистой функции. Проект: [technical design](../../specs/scheduled_deletion_design.md).

## Ограничения текущего кода

SubscriptionService.cancel отменяет продление только последней ACTIVE/TRIAL
подписки. У deletion worker нет billing adapter, список processors по умолчанию
пуст. Restore завершает удаление без сверки подписок. Webhooks обновляют подписку
без проверки deletedAt. Смена локального статуса не подтверждает отмену у провайдера.

## Предлагаемая последовательность реализации

1. Разделить запланированное и окончательное удаление. При планировании сохранять
   доступ до конца оплаты и устойчивую операцию отключения продления для каждой
   подписки. Блокировать и очищать при наступлении даты удаления или выборе
   «Удалить сейчас». Удаление не считать заранее завершённым.
2. До подтверждения хранить ссылки провайдера в ограниченном операционном
   хранилище. Использовать общий внутренний billing port для удаления и restore,
   без зависимости worker от API host. Границу согласовать до реализации.
3. Вызывать отмену вне транзакции БД со стабильным ключом операции. Проверять
   состояние провайдера: timeout или отсутствие adapter означают ожидание, а не
   успех. Повторять с задержкой и эскалировать в пределах утверждённых сроков.
   После неоднозначного ответа сначала сверять состояние.
4. Поздние, повторные и переставленные webhooks не должны возвращать доступ или
   продление удалённому аккаунту. Для сверки сохранить минимальное ограниченное
   соответствие идентификаторов; срок определить до удаления ссылок провайдера.
5. Подтверждать удаление у processor отдельно от отмены подписки. Завершать receipt
   только после подтверждения всех необходимых processors.
6. Не менять обязательные договоры, счета и отчёты выплат в этом срезе. Отдельно
   спроектировать изолированное хранение и доступ; не удалять каскадно и не считать
   обязательные связи этих документов с User уже разорванными.
7. После restore восстановить ожидающие операции из независимого ledger и сверить
   провайдера до включения трафика и фоновых операций с внешними эффектами.

## Решения до реализации обработчиков

- Правила возвратов и уже выставленных счетов, включая сценарий «Удалить сейчас».
- Одобренный провайдер, adapter и возможности подтверждения отмены/удаления.
- Схема ограниченного соответствия идентификаторов, категория хранения, срок и
  ответственный; обработка поздних webhooks после очистки продуктовых ссылок.
- Согласованная общая billing-граница и схема устойчивых операций/ADR.

## Обязательные тесты

Несколько подписок; trial без провайдера; отсутствующий adapter; timeout с
последующим подтверждением; повторная доставка; падение после удалённого успеха
до commit; webhook после удаления; restore старой подписки; неизменность чужих
аккаунтов и финансовых документов. Recovery остаётся красным до разрешения сверки.

## Изменение audit metadata в этом срезе

Обычное удаление и restore используют общий транзакционный helper. У записей,
связанных через actor, entityId или прежний subject actor, metadata становится
SQL NULL, actor/entityId псевдонимизируются. Сохраняются id/action/entity/createdAt
как минимальное событие. Безопасные JSON-поля не угадываются: вложенные данные
удаляются целиком. Чужие записи не меняются. Ссылки только внутри metadata без
этих связей и полная необратимость разрыва связей данным helper не покрыты.
