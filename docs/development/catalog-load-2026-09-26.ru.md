16 028 байт: примерно в 41,5 раза меньше. Варианты фильтров — 1827 байт;
старый ответ таксономии с вложенным содержимым — 1 213 965 байт. Эти ответы
имеют разный состав; новый frontend получает только нужные ему данные.

от старой, поэтому их RPS нельзя выдавать за общий коэффициент ускорения.

## Найденная и исправленная проблема

Первый запуск `3b5b35cd449348fabf3a3554ec4c8acc` завершился FAILED:
запрос вариантов фильтров был настолько медленным, что этапы с параллельностью
1 не набрали минимум пять ответов на маршрут. HTTP-ошибок не было, очередь
прошла проверку, временная БД удалена. При 1000 видео/20 запросах p95 вариантов
фильтров составлял 5087,8 мс, страницы — 2469,1 мс.

EXPLAIN ANALYZE на тестовой БД показал около 945/749 мс JIT-компиляции в
запросах областей/позиций. Прямые и производные связи разделены на отдельные
SELECT внутри той же RepeatableRead-транзакции, результат объединяется по ID.
Эквивалентные диагностические планы исполнялись менее 1 мс без JIT.
Настройки PostgreSQL глобально не менялись, кеш ответов не добавлялся.

## Проверки и оставшиеся ограничения

- `pnpm verify`: успешно, включая формат, архитектуру, lint, типы, unit и сборки.
- API integration: 17 тестов, восемь файлов; пять сценариев каталога, включая
  производные позиции без прямой связи с видео и отсутствие дубликатов.
- В первом запуске integration исправлено обязательное поле `reactions: []`
  тестового урока; assertions и поведение приложения не ослаблялись.
- `pnpm load:test`: три теста прошли после выдачи разрешения на дочерний процесс;
  первоначально sandbox возвращал `spawn EPERM`.
- Очередь: 250 событий за 1,42 секунды; 250 повторных доставок оставили ровно
  250 эффектов, без ошибок и dead letters. Обработчик — no-op.
- Браузерные тесты в этом продолжении не повторялись: frontend не менялся;
  ранее прошли 27 public-тестов и семь финальных проверок каталога.
- Remote CI, настоящие провайдеры, длительная нагрузка и production SLO
  остаются непроверенными. Успешный локальный прогон не означает готовность запуска.
