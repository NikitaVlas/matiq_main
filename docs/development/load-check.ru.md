# Локальная нагрузочная проверка

## Запуск

1. Запустить Docker Compose: `docker compose up -d`.
2. Проверить измеритель: `pnpm load:test`.
3. Выполнить `pnpm load:check` (в PowerShell при необходимости `pnpm.cmd`).

Сценарий собирает backend, API и worker. Использует только локальные Compose
PostgreSQL `127.0.0.1:5432` и Redis `127.0.0.1:6379`, создаёт новую БД
`matiq_load_<uuid>` и очередь `matiq-load-<uuid>`. Основная БД не заполняется и не
очищается. После завершения удаляются только созданные этим запуском ресурсы.
Адреса подключения не настраиваются через переменные среды; `.env` приложения не
загружается в процесс API. Внешние провайдеры не вызываются.

JSON-отчёт и журнал API: `test-results/load/<uuid>/`. Код завершения ненулевой при
ошибках HTTP/содержимого, недостаточном числе выборок, отказе очереди или очистки.
При аварийном завершении всего процесса могут остаться ресурсы с UUID запуска;
перед ручным удалением сверить точное имя с отчётом/каталогом этого запуска.

## Методика

- Два размера: 100 и 1000 синтетических опубликованных видео с описаниями,
  связями с таксономией, 20 курсами и пятью тренерами.
- Отдельный процесс собранного API слушает случайный порт только на loopback.
- Четыре маршрута: `/content/videos`, `/content/catalog`, `/content/courses`,
  `/content/trainers`; равномерное чередование, 1/5/20 параллельных запросов.
- Каждый этап запускает запросы восемь секунд; завершение последних запросов
  включено в elapsed/throughput. Таймаут запроса 10 секунд. Перед замерами —
  запрос прогрева к каждому маршруту. Минимум пять ответов на маршрут/этап.
- Измеряются полное получение и JSON-проверка ответа, p50/p95/p99/max, ошибки,
  статусы, средний размер ответа и число запросов в секунду.
- Процесс API сообщает CPU time, пиковый RSS с интервалом 100 мс и p99 задержки
  event loop (разрешение 20 мс). Снимки `pg_stat_database` включают сам измеритель
  и обновляются PostgreSQL асинхронно; это диагностические счётчики, не profiler.
- Чистые функции фильтра из исходного frontend-кода выполняются в Node:
  восемь списков вариантов, шесть совместных фильтров и поиск; 10 прогревочных и
  100 измеряемых итераций. Проверяется ожидаемое количество результатов.
- 250 событий проходят настоящий outbox dispatcher, Redis/BullMQ и inbox
  consumer с параллельностью 5. Обработчик безопасный no-op. Проверяется
  завершение за 60 секунд, затем 250 повторных доставок без повторения эффекта.

## Интерпретация и ограничения

Это короткий локальный closed-loop baseline: новый запрос начинается после
предыдущего ответа. Он не моделирует независимый поток прибывающих запросов,
длительный пик, медленную сеть или число одновременно активных спортсменов.
Ошибки и недостаточная выборка блокируют успешный результат; пороги latency и
production SLO ещё не утверждены, поэтому скорость фиксируется без выдуманного
критерия готовности к запуску. Малые выборки p99 не дают устойчивой оценки хвоста.

Браузерный рендеринг, задержка ввода фильтров, авторизованные записи, доставка
писем, обработка видео и платежей этим сценарием не проверяются. No-op throughput
нельзя переносить на реальные задания. Для запуска нужны сервер, реальные
обработчики, целевой профиль трафика, soak-тест и повторные замеры.
