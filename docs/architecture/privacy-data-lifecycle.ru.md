# GDPR, хранение в ЕС и жизненный цикл данных MATIQ

## Область и принципы

MATIQ проектируется по принципам минимизации, ограничения целей, точности,
ограничения хранения, конфиденциальности и доказуемой ответственности.
Документ задаёт инженерный baseline, но не заменяет юридическую консультацию.

Основные пользовательские данные, видео, журналы, аналитика и резервные копии
размещаются в ЕС. Международный сервис допускается только после отдельного
согласования, проверки DPA, subprocessors, места обработки, механизма
международной передачи и возможности удаления/экспорта.

## Категории данных

| Категория         | Примеры                            | Правило                                           |
| ----------------- | ---------------------------------- | ------------------------------------------------- |
| Account           | email, password hash, sessions     | Не хранить пароль; защищать и ограничивать доступ |
| Athlete profile   | дисциплина, пояс, опыт, цели       | Только для профиля и рекомендаций                 |
| Health limitation | добровольная общая отметка         | Без диагнозов и свободного медицинского текста    |
| Assessment        | ответы, score, rule version        | Версионирование и ограниченный доступ             |
| Viewing           | позиции и подтверждённые интервалы | Минимизация raw events и anti-abuse               |
| Commerce          | customer/order/payment references  | Не хранить карточные реквизиты                    |
| Trainer finance   | договоры и payout reports          | Отдельные permissions и юридические сроки         |
| Audit/security    | actor, action, reason, signals     | Минимизация и защита от изменения                 |

Перед production владелец продукта с юристом фиксирует controller identity,
правовые основания, privacy notice, record of processing, DPIA necessity и
сроки по каждой категории.

## Права пользователя

Система должна поддерживать:

- доступ и машиночитаемый экспорт;
- исправление данных;
- удаление аккаунта;
- ограничение/возражение, где применимо;
- отзыв необязательных согласий без потери законно необходимой обработки.

Запрос идентифицируется безопасно, имеет audit trail и не раскрывает данные
другого человека.

## Удаление аккаунта

1. Пользователь открывает отдельный destructive flow в профиле.
2. Система показывает последствия и требует повторную аутентификацию.
3. Активные sessions отзываются; подписка обрабатывается по прозрачным
   правилам, чтобы удаление UI не создало новое списание.
4. Account блокируется и создаётся idempotent deletion job.
5. Прямые идентификаторы удаляются или необратимо псевдонимизируются во всех
   продуктовых модулях и у processors.
6. Данные, которые требуется хранить по закону, изолируются, минимизируются и
   больше не используются для продукта.
7. Резервные копии не изменяются точечно, но удалённые данные не
   восстанавливаются в активную систему и исчезают по backup-retention cycle.
8. Пользователь получает подтверждение завершения.

Статус подтверждения доступен 30 дней по отдельному случайному secret, который
возвращается только один раз при создании запроса. В базе хранится только его
SHA-256 hash; status endpoint не раскрывает email, исходный user ID или состав
сохранённых по закону записей.

## Защита восстановления из backup

Перед созданием каждого backup оператор экспортирует актуальный deletion ledger
в хранилище, независимое от backup основной PostgreSQL:

`pnpm --filter @matiq/worker privacy:ledger:export -- <ledger-path>`

Ledger содержит только случайный `privacySubjectId` и даты запроса/хранения — без
email и внутреннего user ID. После восстановления backup и **до открытия API и
Worker для обычного трафика** оператор применяет сохранённый ledger:

`pnpm --filter @matiq/worker privacy:ledger:reapply -- <ledger-path>`

Команда идемпотентно восстанавливает tombstones и повторно удаляет либо
псевдонимизирует вернувшиеся записи. Backup/restore runbook обязан считать
неуспешное применение ledger блокером запуска. Tombstones хранятся 35 дней,
соответственно rolling backup window; доказательство GDPR-запроса продолжает
храниться по отдельному трёхлетнему сроку.

История просмотра и assessment после удаления не должна позволять восстановить
личность. Финансовые и audit-записи могут сохраняться только на
документированном основании.

## Утверждённая матрица хранения

Сроки ниже являются утверждённым инженерным ориентиром. Они не разрешают
бессрочное хранение и должны быть подтверждены немецким юристом или
Datenschutzbeauftragter до production.

| Данные | Срок хранения | Действие после срока |
| --- | --- | --- |
| Аккаунт, профиль, assessment и Roadmap | Пока аккаунт активен | После подтверждённого запроса аккаунт блокируется сразу; продуктовые данные удаляются или необратимо псевдонимизируются в течение 30 дней |
| История просмотров и прогресс | Пока аккаунт активен | Удалить в течение 30 дней после подтверждённого удаления аккаунта |
| Playback sessions и raw heartbeat | 90 дней с момента создания | Необратимо удалить |
| Verified watch intervals | 180 дней после закрытия расчётного месяца | Удалить viewer-level записи; оставить только обезличенный месячный агрегат |
| Auth events и security logs | 90 дней | Удалить, кроме записей под документированным incident/legal hold |
| Технические application logs | 30 дней | Необратимо удалить |
| Admin audit log | 5 лет | Удалить; при удалении аккаунта раньше срока необратимо заменить идентификаторы subject, сохранив минимально необходимую доказательную запись |
| Доказательство выполнения GDPR-запроса | 3 года с конца календарного года завершения | Удалить; в течение срока хранить только request ID, даты, статус и обработанные системы без email, имени и исходного user ID |
| Использованные/просроченные verification и reset tokens | До использования или expiry плюс 7 дней | Удалить запись и hash токена |
| Просроченные или отозванные sessions | Не более 24 часов после expiry/revoke | Удалить |
| Успешный Outbox | Зашифрованный payload — 24 часа после обработки; безопасные технические metadata — 30 дней | Сначала очистить payload, затем удалить запись |
| Завершённый Inbox | 30 дней | Удалить |
| Dead-letter | 30 дней; максимум 90 дней при открытом расследовании | Удалить после закрытия или достижения максимального срока; payload не копировать |
| Бухгалтерские подтверждения: invoices, refunds, chargebacks, payout reports | 8 лет с конца соответствующего календарного года | Удалить после окончания обязательного срока, если нет legal hold |
| Книги, годовая отчётность и соответствующие записи | 10 лет с конца соответствующего календарного года | Удалить после окончания обязательного срока, если нет legal hold |
| Коммерческая переписка и договоры тренеров | 6 лет с конца календарного года окончания договора или получения/отправки документа | Удалить после окончания обязательного срока, если более долгий срок не применяется к конкретному финансовому документу |
| Резервные копии MATIQ | Rolling window 35 дней | Данные исчезают при ротации; после restore журнал удалений применяется до открытия системы для обычной обработки |
| Активные копии у processors/providers | Не более 30 дней после команды удаления | Получить подтверждение удаления или зафиксировать исключение и escalation |
| Backup-копии у processors/providers | Не более 90 дней | Требование закрепить в DPA/договоре и проверить до подключения provider |

Срок считается от указанного события до конца соответствующих суток, если для
категории не указан отсчёт от конца календарного года. Retention job должен быть
идемпотентным, аудируемым и не сохранять удаляемый payload в логах.

## Удаление, псевдонимизация и legal hold

Необратимо удаляются direct identifiers, credentials/MFA data, assessment
answers, персональный Roadmap, viewing history, playback records, auth tokens и
завершённые delivery payload. Простой hash предсказуемого user ID не считается
необратимой псевдонимизацией.

Псевдонимизируются только записи, которые требуется сохранить на отдельном
документированном основании: audit events, обезличенные viewing aggregates и
финансовые итоги без данных зрителя. Обязательные бухгалтерские документы
сохраняют только реквизиты, требуемые законом, изолированы от продуктового
профиля и недоступны для продуктовой аналитики.

Legal hold приостанавливает удаление только конкретной категории и конкретного
периода. Для него обязательны основание, ответственный, дата окончания и
пересмотр не реже одного раза в 90 дней. Бессрочный hold всего аккаунта запрещён.

## Требования к внешним providers

Команда удаления отправляется каждому processor/provider не позднее 24 часов
после запуска соответствующей фазы локального удаления. Новый provider может
быть подключён только если договор или DPA фиксирует удаление активных копий не
позднее 30 дней, backup-копий не позднее 90 дней, помощь с data-subject requests,
список subprocessors и проверяемое подтверждение удаления. Более длинный срок —
отдельный production blocker и требует документированного юридического решения.

## Правовая опора

- [GDPR Articles 5 и 17](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32016R0679):
  data minimisation, storage limitation, право на удаление и законные исключения.
- [HGB § 257](https://www.gesetze-im-internet.de/hgb/__257.html) и
  [AO § 147](https://www.gesetze-im-internet.de/ao_1977/__147.html): 10 лет для книг/годовой отчётности, 8 лет для
  бухгалтерских подтверждений и 6 лет для коммерческой корреспонденции.
- [BGB § 195](https://www.gesetze-im-internet.de/bgb/__195.html) и
  [§ 199](https://www.gesetze-im-internet.de/bgb/__199.html): общий трёхлетний
  срок исковой давности и его отсчёт.

## Безопасность и incident response

- encryption in transit и at rest;
- least privilege, MFA для Admin/Editor, re-authentication для критических
  действий;
- отдельный доступ к финансовым, assessment и security данным;
- redaction секретов и персональных данных в логах;
- журнал processors и data locations;
- процедура обнаружения, оценки и уведомления о breach;
- регулярная проверка восстановления backup в ЕС.

## AI и персональные данные

AI получает минимальный структурированный payload без email, health limitation,
сырых ответов, если они не нужны объяснению, и иных идентификаторов. Provider
не может использовать данные для обучения без отдельного согласования. При
отказе AI детерминированный результат остаётся доступен без объяснения.

## Production gates

- юридически проверенные privacy notice, terms и processor agreements;
- юридическое подтверждение утверждённой инженерной retention schedule;
- реализованные export/delete workflows;
- проверенное удаление у processors и из восстановленных backup;
- DPIA decision;
- incident-response и data-breach playbook.
