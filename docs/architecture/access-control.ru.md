# Модель доступа и редакционного процесса MATIQ

## Роли

MATIQ использует четыре системные роли:

| Роль      | Назначение                                                      |
| --------- | --------------------------------------------------------------- |
| `Athlete` | Assessment, Roadmap, подписка и просмотр контента               |
| `Trainer` | Только собственная статистика и финансовые отчёты               |
| `Editor`  | Подготовка контента и методологических сущностей                |
| `Admin`   | Полное управление, публикация, видео, assessment и безопасность |

Отдельная роль методолога в первой версии не используется.

## Принцип авторизации

Доступ проверяется по конкретному permission на сервере. Название роли само по
себе не заменяет проверку разрешения.

```text
Authenticated user
        ↓
Role
        ↓
Permission
        ↓
Resource scope
        ↓
Authorised action
```

## Ответственность Editor

`Editor` может создавать и редактировать черновики:

- тренеров;
- курсов;
- модулей и уроков;
- позиций и PositionContext;
- SkillGroup;
- техник и TechniqueVariant;
- Movement;
- Drills;
- Flows;
- описаний, связей и основной темы загруженного видео.

`Editor` не может:

- загружать видео;
- публиковать или архивировать контент;
- изменять assessment;
- управлять пользователями и ролями;
- управлять платежами;
- изменять audit log.

## Ответственность Admin

`Admin`:

- загружает видео;
- выполняет все разрешённые редакторские действия;
- публикует, снимает с публикации и архивирует контент;
- создаёт вопросы, ответы, ветвление и правила assessment;
- управляет пользователями и ролями;
- получает доступ к подпискам и отчётам;
- просматривает audit log.

Критичные действия могут потребовать отдельного permission даже для `Admin`.

## Жизненный цикл контента

```text
DRAFT
  ↓ отправка на проверку
IN_REVIEW
  ↓ одобрение Admin
PUBLISHED
  ↓ снятие с публикации
ARCHIVED
```

Допустимые переходы:

- `Editor` создаёт и изменяет `DRAFT`.
- `Editor` отправляет `DRAFT` в `IN_REVIEW`.
- `Admin` возвращает `IN_REVIEW` в `DRAFT`.
- Только `Admin` переводит `IN_REVIEW` в `PUBLISHED`.
- Только `Admin` переводит `PUBLISHED` в `ARCHIVED`.
- Повторная публикация требует повторного одобрения `Admin`.

Переименование статусов возможно при проектировании интерфейса, но смысл
переходов должен сохраняться.

## Ревизии опубликованного контента

Опубликованный материал нельзя редактировать напрямую:

1. Из опубликованной версии создаётся новая черновая ревизия.
2. `Editor` или `Admin` изменяет черновую ревизию.
3. Ревизия проходит `IN_REVIEW`.
4. `Admin` публикует ревизию.
5. Новая версия заменяет активную, а предыдущая остаётся в технической истории.

Снятие материала с публикации требует обязательной причины, которая сохраняется
в audit log.

## Публикация связанных данных

Материал нельзя публиковать, если обязательные связи не готовы. Предварительно:

- у видео есть загруженный и готовый видеоресурс;
- задана одна основная тема;
- указана дисциплина;
- заполнены обязательные немецкие тексты;
- связанный тренер существует;
- все обязательные методологические сущности опубликованы;
- отсутствуют критические ошибки проверки.

Точные правила определяются для каждого типа контента отдельно.

## Audit log

Audit log сохраняет:

- автора действия;
- роль и permission;
- время;
- тип и идентификатор сущности;
- тип операции;
- изменённые поля до и после;
- причину, если она обязательна;
- технический контекст запроса без секретов.

Необходимо аудитировать:

- создание и изменение контента;
- изменение статуса публикации;
- загрузку и замену видео;
- изменение assessment и экспертных правил;
- изменение ролей и permissions;
- административные действия с подписками;
- просмотр или экспорт чувствительных отчётов, если это потребуется.

Предварительный срок хранения audit log — не менее 5 лет. Окончательный срок и
правила удаления должны быть проверены с учётом GDPR, договорных и юридических
требований до production.

## Усиленная аутентификация

- MFA обязательна для `Admin` и `Editor`.
- Критичное действие требует недавней повторной аутентификации.
- Повторная аутентификация не заменяет проверку permission и MFA.

Критичные действия:

- изменение роли или permissions;
- удаление или блокировка пользователя;
- изменение вопросов, ветвления или правил assessment;
- снятие контента с публикации;
- административное действие с подпиской.
- активация договора тренера, утверждение расчётного отчёта и фиксация выплаты.

## Ограничения

- `ACL-001`: Авторизация выполняется на сервере.
- `ACL-002`: `Trainer` видит только собственные данные.
- `ACL-003`: `Editor` не загружает видео.
- `ACL-004`: Только `Admin` публикует и архивирует контент.
- `ACL-005`: Только `Admin` изменяет assessment и правила оценки.
- `ACL-006`: Изменение ролей и permissions доступно только `Admin`.
- `ACL-007`: Административные изменения создают audit event.
- `ACL-008`: Audit log нельзя изменять через обычные административные функции.
- `ACL-009`: Наличие маршрута в интерфейсе не предоставляет permission.
- `ACL-010`: Изменение критичных permissions требует отдельного согласования.
- `ACL-011`: Опубликованный контент изменяется только через новую ревизию.
- `ACL-012`: Снятие контента с публикации требует причины.
- `ACL-013`: MFA обязательна для `Admin` и `Editor`.
- `ACL-014`: Критичные действия требуют повторной аутентификации.
- `ACL-015`: Audit log предварительно хранится не менее 5 лет; срок требует
  юридической проверки до production.
